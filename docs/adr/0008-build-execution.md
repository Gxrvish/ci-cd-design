# ADR-0008: Build execution: one BuildKit solve, steps read from its progress

Status: accepted 2026-11-06 (Gate B part 3).
The detection engine and one strategy are YOU BUILD IT in M5. This ADR fixes the execution path and the step model, not the strategies.

## Context

- Spec 10: every plan ends as a Dockerfile, generated by a strategy or provided by the user. One execution path builds it with BuildKit and pushes the image. Tests run either as a build stage or as a container started from the build-stage image. Installing and building must not happen twice.
- Spec 10 also asks to compare two ways of getting per-step status and logs: parse BuildKit's structured progress, or run the steps separately.
- Overview rule 3 (accepted): the runner talks only to buildkitd, never to dockerd, provided tests run as a build stage. This ADR confirms that.
- ADR-0006 left per-step log views to this ADR.

## Evidence

- `[SOURCE]` The BuildKit Go client streams progress while it builds: `Solve(ctx, def, opt, statusChan chan *SolveStatus)`. Each `SolveStatus` carries:
  - vertices, with digest, name, start and end times, a cached flag and an error;
  - progress statuses;
  - log lines tagged with the vertex digest and the stream (stdout or stderr).

  Source: buildkit `client/solve.go:82`, `client/graph.go:10-54` (Apache-2.0). `buildctl --progress=rawjson` prints the same data (Gate A, section 3).
- `[SOURCE]` The Dockerfile frontend names each instruction's vertex `[<stage> <n>/<total>] <instruction>` when its stage has a name (`frontend/dockerfile/dockerfile2llb/convert.go:2068-2085`).
- `[DOCS]` "BuildKit only builds the stages that the target stage depends on" (https://docs.docker.com/build/building/multi-stage/).
- `[SOURCE]` Runbot runs one container per config step (Gate A, section 1.2). That is the "run steps separately" model.
- `[DOCS]` Go 1.24 added `os.Root`. Its methods "do not permit paths that refer to locations outside the directory, including ones that follow symbolic links out of the directory" (https://go.dev/doc/go1.24).

## Options

1. **One solve per build.** The strategy writes a multi-stage Dockerfile with named stages. The runner maps progress vertices to steps by stage name.
2. **One solve per step.** Build target `deps`, then `build`, then `test`, then `runtime`. The shared cache lets each solve reuse the previous one.
3. **Steps as separate containers**, the Runbot model: run install, build and test in containers that share a workspace, then build the image.

## Decision

Option 1.

### Steps of one attempt

| Step | Runs in | What happens |
|---|---|---|
| `clone` | runner | Fetch exactly the job's commit into a directory for this attempt: depth 1, no submodules, no LFS. |
| `detect` | runner | The strategy's `Detect` and `Plan` read files through `os.Root`, so a symlink in the repository can't make them read outside the checkout. Nothing from the repository executes. |
| `install` | BuildKit, stage `deps` | Install dependencies. |
| `build` | BuildKit, stage `build` | Build the app. |
| `test` | BuildKit, stage `test` (optional) | Run the tests. |
| `image` | BuildKit, stage `runtime` and the exporter | Assemble the final image. |
| `push` | BuildKit exporter | Push it, then report the digest. |

### Tests inside the same solve

- BuildKit skips stages the target doesn't depend on, so a plain `test` stage would never run.
- When tests are on, the `test` stage ends by creating an empty marker file, and the `runtime` stage copies it: `COPY --from=test /cf-tests-passed /cf-tests-passed`. That one line makes the image depend on the tests.
- A failing test fails the solve, so nothing is pushed.
- The `runtime` stage can build in parallel with `test`; only the final copy waits.

### User Dockerfiles

- The Dockerfile strategy has no stage convention. All of its vertices map to the `build` step, plus `image` and `push`.
- Tests are the user's business inside their own Dockerfile. There is no separate test step `[OUR DECISION]`.

### Mapping vertices to steps

- A vertex named `[deps …]` belongs to `install`, `[build …]` to `build`, `[test …]` to `test`, `[runtime …]` to `image`.
- Everything else (base image metadata, export, push) goes to `image` or `push`. `[INFERRED]` The exact names of the export and push vertices are checked in the M1 internals lab.
- A step starts when its first vertex starts and ends when its last vertex completes.
- An error in a vertex fails its step. A cached vertex counts as succeeded, and the UI shows it as cached.

### Logs per step

- The runner prefixes each line with its step: `[install] added 312 packages`.
- The UI filters by prefix.
- No schema change to ADR-0006.

### Image name

`<registry>/<org>/<project>:<sha12>-b<build>-a<attempt>`.

- It carries the commit SHA and the build ID (spec 5.2.5) and is unique per attempt.
- This refines the tag example in ADR-0003.
- Deployments use the digest, never the tag.

### Cache and secrets

- **Local cache:** each runner's buildkitd keeps its own cache (ADR-0009).
- **Cache mount ids:** generated Dockerfiles prefix them with the project id, for example `id=p42-npm`.
- **Registry cache export** (`type=registry,mode=max`) waits until an organization has several runners (M9).
- **Build-phase variables** go through secret mounts only (ADR-0007).

### Cancel and timeout

- The runner cancels the solve's context.
- Whether buildkitd then kills running `RUN` processes, and what happens when the client simply disappears, is verified in the M1 break-it session (`failures-and-targets.md`).

## Why

- **Option 1** keeps a single solve: one progress stream, one cache, one result. BuildKit runs independent stages in parallel. Vertex names already contain the stage, so per-step status costs a prefix match.
- **Option 2** adds a solve round trip per step, and each later solve has to re-check the cache of the earlier stages. Its step boundaries are cleaner, but we don't need that.
- **Option 3** does the install and build work once in the step containers and again for the image, which spec 10 forbids. It also needs a container runtime for the runner, which brings the Docker socket back.
- **Tests as a stage instead of a container from the build-stage image:** running a container needs dockerd or another runtime in the runner (overview rule 3). Inside the solve, tests get the same sandbox, limits and cache as the build.

## Consequences

- **Dependency:** the runner uses the BuildKit Go client (Apache-2.0).
- **Stage names are a contract:** generated Dockerfiles must use `deps`, `build`, `test` and `runtime`. The M5 strategy unit tests check this.
- **Steps overlap in time** because BuildKit runs stages in parallel. The UI shows each step's start and end, not a strict sequence.
- **Not collected:** test reports such as JUnit files. Test output lives in the `test` step log, and the `report` artifact kind in the data model stays unused until a milestone needs it.
- **Test services** (for example a database the tests need) are out of scope `[OUR DECISION]`.
- **The runner clones hostile repositories itself**, and it is a trusted process that holds the claimed job's secrets. A bug in Git triggered by repository content would land there.
  - Mitigation: fetch one commit, no submodules, no LFS, and keep Git up to date.
  - Stronger alternative, not planned: let BuildKit fetch the Git source inside its sandbox and read the files needed for detection through the BuildKit gateway, so repository bytes never touch the runner.
